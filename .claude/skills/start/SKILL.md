# /start

人が関わるのは「1の質問に答える」「6で目で見る」「PRを確認してマージする」だけです。それ以外は確認を求めずに進めます。

## 人に見せるときの書き方

確認する人はエンジニアではありません。質問・issueの下書き・6の確認項目・PRの本文は、次のように書きます。

- 専門用語を使わない。使うときは一言で説明する
- 短く書く。確認項目は1行に1つにし、「どこを開いて・何を見て・どうなっていればOKか」だけを書く
- 人が判断しなくてよいもの(AIが確認済みのもの)は書かないか、最後に短くまとめる

## 止まって聞く条件

- ビルドやPlaywrightの確認が、直しても3回続けて失敗した(試したことを報告する)
- issueに書かれていない仕様上の判断が必要になった(見た目の細かい数値など、デザインスキルで決められるものは除く)

## 1. 要件定義

- 引数がissue番号なら `gh issue view` で読む。要件が十分なら「要件は足りているので実装に進みます」と1行伝えて2へ進む
- それ以外は `mattpocock-skills:grilling` で質問する(issueがあればその内容を前提にする。引数がなければ「何を作りますか？」から聞く)
- 決まった内容をissueの下書きにまとめて見せ、確認が取れてから投稿する。既存のissueには本文を書き換えずにコメントで追記し、なければ新しく作成する

## 2. 準備

1. `git checkout main && git pull`
2. 手元のブランチのうち、`gh pr list --state merged --head <ブランチ>` でマージ済みと分かったものだけを削除する
3. CLAUDE.mdの命名規則でブランチを切る
4. `ponytail:ponytail` を `full` でオンにする

## 3. 実装

デザイン案件は、内容に合うスキルを選ぶ。どれを使ってもサイトの方針と、CLAUDE.mdの演出のルールを優先する。

| 内容 | スキル |
|---|---|
| 見た目の仕上げ・細部 | `emil-design-eng` |
| 新しいページ・大きな見た目の変更 | `frontend-design` |
| 演出・アニメーション | `animate`(カクつくときは `animation-performance`) |
| スマホでの触り心地 | `mobile-native` |

実装が終わったらコミットする(5の修正前に戻れるようにするため)。

## 4〜5. レビューと修正

- mainからの差分を `ponytail:ponytail-review` と `code-review`(`medium`)でレビューし、両方の指摘を直す
- ponytailの指摘が、issueで作ると決めたものとぶつかるときは要件を優先し、そのことをPRに書く

## 5.5. 確認

- `npm run build` を実行する
- 見た目・動きに関わる変更は `npx playwright` で確認する(iOS向けの修正はWebKitで)

## 6. 人に渡す

- サーバーをバックグラウンドで起動する。画像、`/api/*`・`src/worker.ts`、ビュートランジションや読み込み中の演出に関わる変更、または迷うときは `npm run preview`、それ以外は `npm run dev` を使う
- 次の形で渡す
  - 1行目: 使ったコマンドと、それを選んだ理由
  - 確認するページのURL
  - 人が見る項目(3〜5個。どのページの・何を・どう操作して・どうなっていればOKか)
  - Playwrightで確認済みの項目
  - 実機でしか確認できない項目
- 直してほしい点を伝えられたら3に戻る。「OK」と言われたら7へ進む

## 7. PR

- コミットしてpushし、CLAUDE.mdの書式でPRを作る。本文には `Refs #N`(直し切る場合は `Closes #N`)、使ったデザインスキル、要件を優先したレビューの指摘を書く
- 6で確認しなかった項目は `## 確認` に未チェックで残す
- マージはしない
